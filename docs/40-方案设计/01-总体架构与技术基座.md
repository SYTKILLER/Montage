# 01 总体架构与技术基座

> 状态：🟡 已出稿待确认（2026-10-05）。本文决定整个移植的骨架：代码住哪、线程怎么分、ArkTS 与 C++ 的边界画在哪。
> 依据：Q&A 1-13 决策整理 + 本地 SDK 实测核验（见 §2）+ 源项目架构梳理。

---

## 1. 目标与非目标

**目标**：把 Compositor（macOS 图像编辑器，~33k 行 Swift + 2.3k 行 C）移植为鸿蒙 PC（2in1，自由窗口）原生应用，保留其核心能力：图层栈合成、画笔引擎、蒙版、调整层、选区、变换、工程文件；架构上支持后续逐功能补齐（06 层矩阵定优先级）。

**非目标（初版）**：iOS/手机形态适配、多用户协作、iCloud 等价云同步、服务卡片。

## 2. 本地 SDK 核验结论（2026-10-05 实测）

方法：直接 grep 本地 SDK（`DevEco Studio/sdk/default/openharmony/{native/sysroot/usr/include, ets}`）。**结论：官方开发助手回答中两处 API 不存在/有误，已修正**：

| API | 助手说法 | 本地 SDK 实况 | 影响 |

## 3. 顶层模块划分（✅ 已按用户裁决改为"单 HAP + 多 HAR"分层架构）

```
┌───────────────────────────────────────────────────────┐
│ entry（ArkTS HAP，deviceTypes=["2in1"]）                │
│  UI 层（ArkTS，声明式）                                 │
│  ├─ 编辑器骨架（菜单栏/工具栏/画布容器/面板/状态栏）        │
│  ├─ 工具交互层（手势→命令、快捷键、面板 @State 状态）      │
│  └─ 轻量视图数据（图层列表 DTO、缩略图、能力位）           │
│            │ 命令（typed NAPI 函数，小参数）               │
│            │ 事件/版本号（版本 bump + Promise 回调）       │
├───────────────────────────────────────────────────────┤
│ core（HAR 静态共享库：引擎 + 桥接，含 C++ native）        │
│  ├─ src/main/cpp/（CMake）                             │
│  │  ├─ engine/   文档模型、图层、选区、撤销、编辑会话      │
│  │  ├─ tiles/    瓦片存储、PixelMap/GL 纹理桥接           │
│  │  ├─ kernels/  源项目 C 内核原样移植（曲线/魔棒/修复…）   │
│  │  ├─ render/   GLES 管线（FBO DAG、着色器、上传）        │
│  │  ├─ io/       解码/编码/工程包读写                     │
│  │  └─ bridge/   NAPI 导出（typed 函数 + 版本回调）        │
│  └─ src/main/ets/（ArkTS typed 包装 API，供 entry 调用）  │
└───────────────────────────────────────────────────────┘
```

- **单 HAP（entry）+ 多 HAR**（用户裁决）：通用工具、引擎核心库抽 HAR 静态共享库；HAR 编译进 HAP 无额外加载成本，工程结构清晰、后续演进灵活；功能模块增多后再考虑把低频功能（滤镜库等）拆 HSP 按需加载。
- **注意**：HAR 内含 native（.so）的打包与 NAPI 模块注册方式需在 M0 实测确认（登记为 M0 验证项）；若遇阻塞，退路是把 cpp 放回 entry、ArkTS 包装仍留 HAR。
- ArkTS 侧通用 UI 工具（主题 token、日志封装等）后续抽独立 HAR（如 `ui-common`），按需建立。
- C++ 用 CMake 组织；`kernels/` 尽量原样搬运源项目 `.c` 文件（它们只依赖 stdint，无平台依赖）。

## 4. 核心决策 D1：文档模型与编辑逻辑住 C++ 引擎 ✅（2026-10-05 用户确认）

**结论：文档模型（CanvasDocument/ImageLayer/选区/调整参数/撤销历史/瓦片位图）全部放 C++；ArkTS 只承载 UI 与交互状态。**

理由：

1. **撤销系统依赖值语义**：源项目撤销 = 整文档值快照（struct 拷贝 + 不可变 CGImage 共享）。ArkTS 类是引用类型，做整对象图深拷贝昂贵且手写 clone 易漏字段；C++ 值语义 + `shared_ptr` 共享不可变位图是同一设计的自然落地。
2. **位图必须在 C++**（GL 纹理、瓦片、C 内核），撤销要"零像素拷贝地共享位图"，模型必须与位图同侧，否则每次快照都要跨 NAPI 搬像素。
3. **线程约束**：重活在 native 线程（TaskPool 无法传 PixelMap，Q5 已证）。模型若在 ArkTS，每次像素操作都要跨桥同步对象状态，桥上全是流量。
4. **UI 绑定有已证范式**：知识库的 `@StorageProp('xxxVersion')` + build 内真实读取模式，正好承接"引擎版本号驱动 UI 刷新"，不依赖把模型暴露成可观察对象。
5. ArkTS 语法红线（禁结构化类型跨界、类必须显式初始化等）让大型数据建模笨拙；C++ 无此负担。

**代价（明确接受）**：
- ArkTS 不能直接读文档——图层面板等需要引擎导出**轻量 DTO 快照**（图层名/可见性/缩略图句柄/序），配版本号刷新（02 层细化）。
- 一切交互命令化，调试跨语言（用 hilog + 引擎内日志双端打点）。
- ArkTS 侧 `@State` 只放：工具选择、面板草稿参数（levels/curves 滑杆值）、视口命令参数、UI 布局状态。

**被否决的备选**：模型放 ArkTS + 仅像素在 C++——撤销、线程、桥流量三项全劣，弃。

## 5. 线程模型（✅ 已按用户裁决细化：C++ 引擎自持 native 工作线程）

| 线程 | 归属 | 职责 | 禁止 |
|---|---|---|---|
| T1 ArkTS UI 线程 | ArkTS | 全部 UI；手势/键鼠事件→组装命令；面板 @State；图层列表渲染（DTO） | 碰像素、做耗时同步调用、**在非主线程更新 UI（硬规则）** |
| T2 渲染线程 | C++ | 独占 EGL/GL 上下文；NativeVsync 驱动帧循环；消费引擎状态绘制（合成 DAG + 上传脏瓦片 + 覆盖层） | 阻塞等 T3、操作 ArkUI |
| T3 引擎工作线程 | C++（**std::thread 自持线程池**，经 NAPI 异步回调回主线程） | 画笔瓦片固化、调整/滤镜运算、解码导出、工程包 IO | 直接调 GL（GL 全在 T2）、操作 ArkUI |
| T4 ArkTS TaskPool | ArkTS | **仅按下面的数据传输分类表使用** | 传 PixelMap/引擎对象 |

**跨线程数据传输分类（用户裁决，硬规则）**：

| 数据形态 | 传输方式 |
|---|---|
| 小型普通数据 | TaskPool execute 参数/返回值，系统序列化 |
| 大型一次性交接的二进制 | **ArrayBuffer transfer**（所有权转移，零拷贝）；或更优——大数据根本不进 ArkTS，native 侧直接处理 |
| 高频共享且确有必要 | 受约束的 `@Sendable`/`ISendable` 对象 + AsyncLock 或不可变设计 |

**流水线范式**：ArkTS 侧取得的数据（如 picker 读出的 ArrayBuffer）→ 主线程经 NAPI 把**数据指针**交给 C++ 工作线程处理 → 结果经 NAPI 异步回调回主线程 → 主线程更新 UI。**UI 更新必须只在主线程发生，任何 C++ 回调或 TaskPool 线程都不得直接操作 ArkUI 组件。**

**同步原则**：
- 引擎内部一把粗粒度互斥（`std::mutex`）保护文档状态起步（编辑器操作频率低、临界区小，先正确后优化）；T2 每帧加锁取绘制快照（图层列表 + 纹理句柄），临界区控制在微秒级。
- 位图数据**永不过 NAPI 桥**；ArkTS 只见：命令参数（数值/字符串）、版本号、忙碌布尔、DTO 数组、异步结果对象。
- 渲染自驱动：引擎脏了不需要通知 ArkTS——T2 每帧检查引擎脏区标志自绘。ArkTS↔渲染的交互只有视口命令（缩放/平移参数），走引擎状态即可。

## 6. ArkTS↔引擎边界契约（草案，02 层细化）

**命令面（ArkTS → 引擎，typed NAPI 函数，禁用泛型 dispatch）**：
- 会话：`engine_openFile(fd)→Promise<Result>`、`engine_newDocument(w,h)`、`engine_close`
- 视口：`engine_setViewport(zoom, panX, panY)`、`engine_fit()`
- 工具：`engine_selectTool(tool)`、`engine_beginStroke(x,y,pressure)`、`engine_continueStroke(...)`、`engine_endStroke()`、`engine_cancelStroke()`
- 编辑事务：`engine_beginEdit()`、`engine_commitEdit()`、`engine_abortEdit()`、`engine_undo()`、`engine_redo()`
- 图层：`engine_setLayerVisible(id, v)`、`engine_reorderLayers(...)`、`engine_addAdjustmentLayer(kind)` …
- 预览：`engine_setPreviewParams(kind, params)`（面板拖动实时预览，轻量参数）

**事件面（引擎 → ArkTS）**：
- 文档版本：引擎变更后 `docRevision++`，经 NAPI 回调写入 AppStorage `docVersion` → 各 `@StorageProp` 建立刷新依赖（知识库已证范式：**build 内必须真实读取**）
- 异步结果：Promise resolve `{ok: true, data} | {ok: false, error}` 模式（ArkTS 异常规范：禁裸 reject、禁吞错）
- 忙碌：`engineBusy` 布尔 + 250ms 防闪烁（对应源项目 showsBusy）
- 图层列表：`engine_getLayerListSnapshot() → DTO[]`（轻量值对象数组），UI 按版本号拉取

**错误模型**：错误码枚举 + 消息，ArkTS 侧映射为 Result 对象；不跨桥抛异常。

## 7. 渲染线程与 GL 上下文管理

1. ArkTS 侧 `XComponent(type: SURFACE)` 承载画布；`OH_ArkUI_SurfaceHolder`（绑定 node）监听 Surface Created/Changed/Destroyed。
2. SurfaceId → `OH_NativeWindow_CreateNativeWindowFromSurfaceId` → T2 线程创建 EGL 上下文（**"谁使用谁绑定，用完即释放"**，Q4 实践要点）。
3. T2 循环：`OH_NativeVSync_RequestFrame` → 检查脏区/视口变化 → 合成（FBO DAG）→ `eglSwapBuffers`。无脏区且无动画（蚂蚁线等）时跳帧省电（LTPO 分档：交互中 expected=120/min=90，静止停请求）。
4. Surface 销毁（窗口缩小/隐藏）时释放 drawable，重建时按 `Changed` 回调的尺寸重配 FBO。

## 9. 风险登记

| 风险 | 缓解 |
|---|---|
| 源项目主线程模型 → 多线程引擎的并发正确性 | 粗锁起步 + 写操作串行队列；M0 起引擎单测（native 侧可先跑 PC 端 C++ 测试再进设备） |
| GL/显示器行为模拟器与真机差异 | **当前以模拟器为唯一开发环境（用户暂无 PC 真机）**；涉及 GL 行为的结论标记"模拟器实证"，设备就绪后集中回归一轮 |
| DMA/stride 语义细节 | M0 实测脚本；自分配缓冲一律按 stride 步进 |
| 撤销快照内存预算 | 沿源项目双限（条数+独占字节）+ onMemoryLevel 联动清理 |
| GLES 管线工作量（最大单项） | 03 层先出着色器清单与最小组（normal 混合+蒙版+透明度）再扩展 |
| NAPI 边界膨胀 | 命令函数白名单制度：新增跨桥函数需在本文档登记 |

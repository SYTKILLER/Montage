## 1. 源模型 → 引擎类型映射总表

## 2. D2.1 像素存储：全图层稀疏瓦片化 ✅（定案，瓦片 256px）

```cpp
constexpr uint32_t kTileSize = 256;          // 定案：256px（256KB/瓦片 RGBA），见修订记录 R2

struct ImageBuffer {                          // 发布后不可变
    uint32_t width, height, rowBytes;        // rowBytes = stride（64B 对齐），遍历禁止用 width*4
    std::shared_ptr<const uint8_t[]> bytes;  // 内部一律 RGBA8888
};
struct Tile { PixelSource pixels; };          // 像素源抽象，见 D2.4
struct TileGrid {                             // 不可变视图（发布后不再改）
    uint32_t cols, rows;
    std::unordered_map<uint32_t, std::shared_ptr<const Tile>> tiles;  // key = ty*cols+tx；哈希定位 O(1)，稀疏：空白瓦片不存在
};
```

- **瓦片定位用哈希映射**（采纳修订 R1）：`unordered_map` + 索引键；不做四叉树——瓦片坐标即地址，无需空间划分查询；数据量本就全在 native（>10 万瓦片的场景由 C++ 承担，与修订建议一致）。ArkTS 侧永不接触瓦片。
- **脏瓦片追踪（采纳 R4，正式化）**：每个 TileGrid 携带 `revision`；绘制/编辑计算笔刷覆盖的瓦片坐标集合写入 `dirtyTiles`，T2 渲染帧只对 dirty 集合做纹理上传，上传后清位。撤销同理只"复活"旧瓦片引用并标记对应瓦片脏。
- **撤销内存性质（R5 确认）**：History 存整文档值快照（POD 拷贝 + TilesRef 引用换新），未修改瓦片 shared_ptr 共享——**内存占用 ∝ 被修改的瓦片数，与画布尺寸无关**。

**可变→不可变规则（不变量）**：绘制中只有 StrokeDraft 持有可写瓦片；commit 把脏瓦片包成 `shared_ptr<const Tile>` 换入新 TileGrid。**任何已发布的像素缓冲永不原地修改**。

### D2.4 像素源抽象（采纳 R6-建议，预留 DMA 扩展点）

```cpp
class PixelSource {                       // 瓦片像素的抽象接口
  public:
    virtual const uint8_t* mapCpu() const = 0;      // CPU 读（含 GL 上传取数）
    virtual uint8_t* mapCpuWrite() = 0;             // CPU 写（仅构建期）
    virtual OH_NativeBuffer* nativeBuffer() = 0;    // GL/DMA 直通路径（EngineBuffer 返回 nullptr）
    virtual void unmap() = 0;
};
class EngineBuffer : public PixelSource { /* malloc 内存，初版唯一实现 */ };
// 后续 DmaBuffer 同接口实现，瓦片/渲染逻辑零改动（DMA 零拷贝的预留扩展点）
```

上层（StrokeDraft/渲染上传/导出拼装）一律经 PixelSource 接口取数，禁止直接摸裸指针。

### D2.2 OH PixelMap 只在 IO 边界（维持定案）

引擎不持有 PixelMap 作为存储；导入导出管线见 §6。DMA 路径经 D2.4 扩展点后置。

## 3. D2.3 选区：覆盖掩码为主表示 ✅（定案，含轮廓与边界细则）

**主表示：8-bit 灰度软选区掩码**（稀疏瓦片，0-255 覆盖强度），存于 Document 内随撤销；**语义是"软选区强度"而非透明度**（修订 R14 定名）——边缘过渡是羽化效果，非精度损失；与源项目 `coverage()` 的 8-bit 光栅化表示精度同级，无退化。

**蚂蚁线（采纳 R8–R10）**：
- 轮廓提取用 **Marching Squares 等值线**（新 C 内核 `kernels/MaskOutline.c`），阈值 127/255，保证视觉轮廓与掩码边界一致；
- **增量重生成**：只对脏瓦片及其邻接带重新提取，差异合并后更新显示；
- 在 **T3 引擎工作线程**执行（线程模型统一，不用 TaskPool）；
- **命中检测硬规则：一切命中与编辑操作直接查询掩码，绝不走轮廓几何**——蚂蚁线只是视觉反馈。

**跨瓦片连续性（采纳 R11）**：布尔（min/max）逐像素无跨瓦片问题；**羽化/模糊必须跨瓦片带 halo 读取**——执行时把目标区域连同周边瓦片边缘像素（≥模糊半径）合入临时缓冲运算后写回，禁止单瓦片内 clamp 到边缘（对应源项目 AdjustmentSurface 的 halo 余量做法）。

## 4. 撤销历史

```cpp
struct DocSnapshot { Document doc; LayerId activeLayer; uint64_t revision; };
struct HistoryEntry { std::string label; DocSnapshot before, after; };

class History {
  public:
    void beginEdit(std::string label);  // 可嵌套（depth 计数）
    void endEdit();                     // before==after 则丢弃
    bool undo(); bool redo();
  private:
    std::vector<HistoryEntry> undoStack_, redoStack_;
    size_t maxEntries_ = 100;
    size_t maxExclusiveBytes_;          // 独占瓦片字节上限，§7
    uint64_t savedRevision_ = 0;        // 异步保存竞态跟踪（04 层对接）
};
```

与源语义对齐：值快照、嵌套事务、条数+独占字节双向裁剪、revision 跟踪"已保存"。**不变量**：Document 只能整体替换，禁止原地改字段。

## 5. 会话与命令面

**AppStorage 键**（全部走"build 内真实读取"范式）：`docVersion`（文档变更）、`engineBusy`（长操作，250ms 防闪烁在 ArkTS 侧）、`historyVersion`（撤销栈变化）、`importProgress`（0–1，导入进度，见 §6）。

**typed NAPI 命令（M1/M2 范围）**：

```
openFileFromFd(fd): Promise<Result<void>>      // §6 管线
newDocument(w, h): Promise<Result<void>>
setViewport(zoom, panX, panY); fitToWindow(canvasW, canvasH)
```

## 6. 导入导出管线（吸收 2.2 风险 1–5，全部采纳）

### 6.1 导入：分带区域解码，峰值 = 一个解码带

**区域解码是必需项而非优化项（R7 定案）**。流程（T3 引擎工作线程执行，多线程并行）：

```
fd → ImageSource（native）→ getImageInfoSync 取原图尺寸
  → 计算目标瓦片网格（含导入裁剪：仅画布覆盖区域，R7-c）
  → 按行带（band = 8×tile 行，可调）逐带 desiredRegion 解码
      每带：解码（并行按条带切分给多 worker）→ 格式核验 → 切瓦片 → 写入 TileGrid
  → 每带完成回调进度（importProgress = done/total）→ 全部完成 bump docVersion
```

- **内存峰值 = 一个带**（8×256 行 × 画布宽 ×4B，万级画布约数十 MB），不再出现 256MB–3.6GB 级瞬时占用（R7 主诉求）。
- **格式直出（R8 采纳）**：解码 options 显式 `desiredPixelFormat: RGBA_8888`，让解码器直出引擎格式，消除二次转换（知识库已证此参数可用）。格式仍按 `info.pixelFormat` 兜底核验（BGRA 兼容换 R/B，知识库既有结论）。
- **SIMD 双架构转换内核（R8-b 部分采纳，降级为后备）**：直出成立时无需转换内核；若实测某格式绕不开，先写标量 C 转换，确认瓶颈后按 arm64 NEON / x86 SSE-AVX 各自加速（x86 与 ARM 2in1 需两套，登记开放点 O5）。
- **进度反馈（R9-c 采纳）**：`importProgress` 进度条；导入是 IO+CPU 密集操作，必须可见。
- **并行（R9-a 采纳，落点修正）**：并行发生在 **T3 native 工作线程**（std::thread 池），不是 TaskPool——位图不过桥，与 01 层线程模型一致。

### 6.2 PixelMap 生命周期（R10 全部采纳）

- **RAII 封装**：C++ 侧 `PixelMapGuard`（构造获取/析构释放，等价 use{}），IO 路径一律经它持有 PixelMap，任何异常/早退路径保证 release。
- **释放顺序硬规则**：先断开引擎侧引用（TileGrid 拷贝完成）→ 再 release PixelMap，杜绝悬挂访问。
- **取消语义**：文档关闭/`aboutToDisappear` 时若有进行中的导入任务，置取消标志，worker 在带边界检查并退出，Guard 兜底释放。

### 6.3 导出（R12 采纳，含已核验的平台约束）

- **已核验**：native `image_packer_mdk.h` **无增量/Session 打包能力**（API 24）→ 超大画布整图导出受 PixelMap 尺寸/内存双重限制，不可能整图打包。
- 策略：**导出前空白瓦片剔除**（默认做）；导出尺寸 >Limits.maxExportPixels（初版 16384）时**降采样导出**并明确提示；分块编码再拼接需要自研 PNG 编码器（vendored 单文件库，违反零依赖需论证）——登记为 04 层决策项（O6），初版不做。
- 导出同样走 T3 + RAII Guard + 进度。

## 7. 并发规则与预算

1. **一把粗锁** `docMutex`：T1 命令（同步执行）、T2 每帧快照（拷贝图层列表 shared_ptr + 脏集）、T3 提交（换 TilesRef/推快照）都在锁内，临界区微秒级；T3 计算用锁外复制的不可变输入。
2. **TaskPool 使用边界**（与 01 §5 三分类一致）：仅当数据形态天然在 ArkTS（如 picker 读出的小配置文件）才用；位图管线全在 native。
3. **Limits 缺省值**（✅ 维持，可运行时调）：

| 项 | 源（macOS） | 引擎缺省 |
|---|---|---|
| 单边上限 | 30000px | 16384px |
| 文档总像素预算 | ≤800MP | ≤100MP（覆盖 8000×8000=64MP 的 2in1 主力场景），按 totalMem 分档（RAM 查询 API 待核验 O2） |
| 撤销独占字节 | 256MB | 128MB |
| 缓存预算 | 2 亿像素 | 256MB 字节预算 |

## 8. 测试策略

1. `engine/`、`kernels/`（含新增 MaskOutline.c）**零 OH 依赖** → 单测在 Windows 宿主机编译运行；值快照/瓦片共享/撤销语义/轮廓提取先在 PC 测透。
2. `tiles/`、`io/`、`bridge/` → 模拟器（Huawei_2in1_Foldable）集成测试（ohosTest）。
3. 撤销一致性 fuzz：随机操作 + 随机 undo/redo，校验共享计数与字节预算。
4. 导入内存峰值回归：大图导入过程采样进程 RSS，断言峰值 ≤ 带 × 常数。

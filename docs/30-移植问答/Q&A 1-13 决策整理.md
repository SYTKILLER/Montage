# Q&A 1-13 决策整理

> 来源：官方开发助手问答，2026-10-05。原始记录：[Q&A 1-13.txt](./Q&A%201-13.txt)；对应提问：[移植阻塞问题清单.md](./移植阻塞问题清单.md)。
> 阅读约定：每个问题按「结论 → 对移植的意义 → ⚠️ 需本地 SDK 核验 → 开放风险」整理。按《开发规范》纪律，**所有 API 在编码前必须以本地 SDK d.ts / native 头文件核验存在性与签名**（核验清单见文末汇总）。

---

## 0. 技术路线定案（P0 问题全部有结论）

| 决策点 | 结论 |
|---|---|
| 画布渲染路径 | **Native XComponent + OpenGL ES**（Q1） |
| 帧调度 | **NativeVsync**（native 线程回调），LTPO 分档设帧率（Q2） |
| 像素上屏 | 解码用 `DMA_ALLOC` 零拷贝；ArkTS↔C++ 用 `NativeBuffer` 共享内存；笔刷脏区用 `writePixelsSync(PositionArea)`（Q3） |
| 图层合成/滤镜 | **`imageEffect` 不覆盖多层 DAG 合成与自定义 GPU kernel → 自写 GLSL shader（NDK + OpenGL ES 3.0 + FBO）**（Q4） |
| C 内核复用 | **可行**：`OH_PixelmapNative_GetPixels` 取裸指针 + `napi_create_async_work` native 异步线程（不走 TaskPool，PixelMap 不可序列化）（Q5） |
| 超大画布 | 单 PixelMap 不可行（3 万 px = 3.6GB），**必须瓦片化** + 区域/降采样解码 + `onMemoryLevel` 内存压力响应（Q6） |
| 浮动面板 | **应用内 Stack 覆盖层**（不用 SUB_WINDOW）（Q10） |
| 菜单栏 | **无系统菜单栏 API → 完全自绘菜单栏**（Row + bindMenu）（Q11） |

**总体判断**：渲染层路线与源项目（Metal 自绘 + 瓦片化 + 不可变像素）高度同构，源项目的瓦片管线/身份缓存设计可以平移到 GL 上；**RAW 是按格式分层的差异化能力**（DNG 可原生显影、其余格式仅预览，Q7），不再是硬缺口。

## 1. 逐题整理

### Q1 渲染路径选型 → Native XComponent + OpenGL ES ✅

- **结论**：官方将"图像处理"列为 XComponent 核心场景；绘制频率 >30fps 或大量像素操作即应切换到 XComponent。ArkUI Canvas 2D 适合低频简单绘制；Vulkan 复杂度过高（留给重度 3D）；OH_Drawing 适合自定义 UI 控件而非完整画布。
- **对移植的意义**：对应源项目的 `CanvasView + CAMetalLayer` → `XComponent + EGL/GLES`；Surface 生命周期管理用 ArkTS 侧 `XComponentController` + Native 侧 `OH_ArkUI_SurfaceHolder`。
- **⚠️ 核验**：`OH_ArkUI_SurfaceHolder` 在本地 native 头文件中的存在性与用法。

### Q2 帧调度 → NativeVsync ✅

- **结论**：两套 API——ArkTS `@ohos.graphics.displaySync`（回调在 UI 主线程，API 12+）与 Native `NativeVsync`（`OH_NativeVSync_Create` 等，回调在**独立 native 线程**，不能直接操作 ArkUI 组件）。帧率别锁死最高值（干扰 LTPO），按内容分档；页面不可见/动画停止时及时 stop 防空跑功耗。
- **对移植的意义**：编辑器画布用 NativeVsync 驱动 GL 渲染循环（等价 CVDisplayLink + MTKView）。native 线程回调 → 与主线程数据交换走原子变量/napi 异步（与源项目"主线程中心 + 脏区上传"模型对应，需重新设计线程边界）。
- **⚠️ 核验**：`OH_NativeVSync_Create_ForAssociatedWindow`（绑定窗口）在 API 24 头文件是否存在；`SetExpectedFrameRateRange` 签名。
- **开放风险**：源项目渲染全部在主线程（MainActor），移植后渲染在 native 线程——Document 值模型的读取同步需要专门的线程方案（这是后续方案设计的重点，不是问答能解决的）。

### Q3 像素上屏与读回 ✅

- **结论**：
  - 解码：`OH_ImageSourceNative_CreatePixelmapUsingAllocator` + `DMA_ALLOC` 内存类型 → GPU 直接访问零拷贝（4K 渲染 20ms → 4ms）；`SHARE_MEMORY` 是普通共享内存（GPU 用需拷贝）。
  - ArkTS↔C++：`editable: true` 的 PixelMap 经 `getNativeBuffer()` + C++ `OH_NativeBuffer_Map` 共享同一物理内存。
  - 笔刷脏区：`writePixelsSync(PositionArea)` 局部更新（比整图裁剪重建快约 7 倍）+ TaskPool 并行填充。
  - 读回：`readPixelsSync(PositionArea)`；读出常为 BGRA_8888，注意 R/B 交换（知识库卡片已有同款结论）；导出耗时大头在像素填充（70–85%），并行填充。
- **对移植的意义**：源项目"256px 瓦片 + 只传脏区"的设计在鸿蒙有直接对应实现；图层像素暂存 PixelMap（SHARE_MEMORY，CPU 算法要读写），合成时上传 GL 纹理。
- **⚠️ 核验**：`CreatePixelmapUsingAllocator`/`DMA_ALLOC` 的 API 级别（答文提到 API 15+，我们 24 满足）；DMA buffer 的 **CPU 写入路径性能**（笔刷高频写 DMA 内存是否合适，还是 CPU 侧画 SHARE_MEMORY、只把合成结果走 DMA）——这一点问答没覆盖，需实测。

### Q4 合成与滤镜 → 自写 GLSL shader ✅（关键决策）

- **结论**：`imageEffect` 是**串行滤镜链**，支持 `OH_EffectFilter_Register` 注入自定义算法，但那是 **CPU 层**的，无法写 GLSL 上 GPU；多层 DAG 合成（图层栈正是 DAG）表达别扭。**官方场景化建议：高性能实时滤镜、复杂自定义 kernel、复杂 DAG 合成 → 自写 Shader（NDK + OpenGL ES 3.0 + FBO）**。
- **对移植的意义**：源项目的 CIImage DAG + Metal compute 管线整体平移为 GLES FBO 管线：混合模式（`glBlendFuncSeparate` / 片元着色器实现 Photoshop 全集）、蒙版混合（CIBlendWithRedMask → shader）、调整层（曲线/LUT 3D 纹理）、特效（可分离膨胀/模糊 → 双 pass blur，对应源项目 MetalLayerEffects 的结构）。答文还给了 GPUImage 式实践要点：`OH_NativeWindow_CreateNativeWindowFromSurfaceId` 桥接、EGL 上下文"谁使用谁绑定、用完即释放"。
- **⚠️ 核验**：`OH_EffectFilter_Register`（若走 imageEffect 兜底）；GL 侧无需核验（标准 GLES 3.0）。
- **工作量提示**：这是移植最大的单项工程——约等于把源项目 Rendering 模块的 Metal/CI 部分重写为 GLES。源项目的着色器源码（Swift 字符串内嵌 GLSL 风格 compute）可作算法参考，但 compute → fragment 需要改写。

### Q5 C 内核复用 ✅

- **结论**：`OH_PixelmapNative_GetNativePixelMap` → `OH_PixelmapNative_GetPixels` 拿裸指针原地处理（注意像素格式、**rowBytes 对齐**、改完可能需 `MarkDirty`）。**推荐 `napi_create_async_work`（native 异步线程）而非 TaskPool**——PixelMap 不可结构化克隆，TaskPool 传不了。架构分层：纯 C 内核（不掺鸿蒙 API）→ NAPI 桥接层 → ArkTS 业务层。
- **对移植的意义**：源项目 2300 行 C 内核（曲线/色阶/魔棒/修复/内容识别填充/抖动等）**可以原样复用**，只需加 NAPI 桥接。与知识库结论互洽（@State 不存像素、native 线程跑重活）。
- **⚠️ 核验**：`OH_PixelmapNative_GetPixels`/`MarkDirty` 在 API 24 头文件的准确签名（答文代码是示意）；`MarkDirty` 是否必要（"视硬件而定"）。

### Q6 超大画布 → 必须瓦片化 ⚠️（重要约束）

- **结论**：PixelMap 序列化上限 **128MiB**（超了渲染失败）；30000×30000 RGBA = 3.6GB **不可能单块解码**。方案：`desiredSize` 降采样解码（缩略图/预览）+ `desiredRegion` 区域解码（放大时按需加载）+ ASTC_4x4 压缩纹理（API 18+，省 3/4 内存但**只能显示不能读像素**）；内存压力用 `onMemoryLevel` 回调分级清理；缓存淘汰只解除引用，批量 release 放在内存告警时机。
- **对移植的意义**：**源项目"瓦片化 + 稀疏快照"的架构不是可选项而是必选项**。图像数据管理（ImportedImage）要按瓦片组设计；128MiB 限制约束的是"进显示链路的单块 PixelMap"，我们自管 GL 纹理不受它限，但受 `GL_MAX_TEXTURE_SIZE` 限制（需运行时查询，一般 4096–16384）。文档限制（单边 30000px、单表面 200MP）在鸿蒙侧要按"瓦片集 + GL 纹理上限"重新校订。
- **⚠️ 核验**：`getImageInfoSync`（原图尺寸）、`desiredRegion` 参数签名；设备实测 `GL_MAX_TEXTURE_SIZE` 与 `onMemoryLevel` 触发行为。

### Q7 相机 RAW → DNG 可原生显影，其余格式仅预览 ❗（追问已更新，需产品决策）

> 2026-10-05 更新：首轮回答后专门追问了 RAW 原始数据能力，结论有实质变化。原始记录：[Q&A 补充-Q7 RAW显影.md](./Q&A%20补充-Q7%20RAW显影.md)。

- **结论**：没有 CIRAWFilter 等价的成品显影滤镜，但能力分两档：
  1. **DNG 格式（API 24 起）**：`imageSource.createImageRawData()` 可获取**传感器原始数据**（buffer + bitDepth）→ 自研显影链可行（黑电平扣除/去马赛克/白平衡/色彩矩阵/Gamma 校正均需自己实现）。
  2. **其他格式（CR2/CR3/ARW/NEF/RAF 等）**：只能解码容器里的**内嵌 JPEG 预览图**（API 22+），拿不到原始数据。
  3. 另据社区反馈，HarmonyOS 6 的 `Image` 组件可直接显示部分 RAW（如 ARW）——仅显示，不解决处理问题。
  - 解码前用 `getImageSourceSupportedFormats()` 动态查询设备支持列表。
- **对移植的意义**：源项目 RawDevelopSheet（曝光/色温/色调实时显影，基于 CIRAWFilter）的等价实现变成**按格式分层**：DNG 可以做到真 RAW 显影（显影链写成纯 C 内核 + NAPI，与 Q5 的架构完全匹配；源项目调整参数恰好对应显影链中段——白平衡/曝光在 gamma 之前施加）；非 DNG 只能预览导入。自研全显影链（含 demosaic）是**不小的图像学工程**，需要独立评估工作量。
- **选项空间（更新后）**：
  1. **分层方案**：DNG 走 `createImageRawData` + 自研显影；非 DNG 走内嵌预览导入（入口保留、UI 注明格式差异）；
  2. **统一降级**：所有 RAW 都走内嵌预览导入（工程量最小，画质受损）；
  3. **v1 砍掉 RAW**，分层方案放到后续版本（DNG 显影作为独立特性立项）；
  4. 集成第三方（LibRaw 移植）——仍违反零依赖原则，除非 DNG-only 路线被证明不够。
  → **待用户决策**；无论选哪个，建议先做一次 DNG `createImageRawData` 的技术验证（拿真实 DNG 文件确认 buffer 布局/Bayer 排列）。
- **⚠️ 核验**：`createImageRawData`/`ImageRawData`（API 24，恰在基线上，必须在本地 d.ts 确认）；`ImageRawData` 的 buffer 是 Bayer 原始排列还是已线性化、bitDepth 取值范围；`getImageSourceSupportedFormats` API 级别。

### Q8 AI 抠图/主体分割 → 可用 ✅

- **结论**：Core Vision Kit `subjectSegmentation`：完全离线、免权限、数据不出端；输出透明前景图（需 `enableSubjectForegroundImage: true`）+ 掩码数组（0-255）+ 边界框；`maxCount` [1,20] 默认 6；要求 RGBA_8888 PixelMap；`init()`/`release()` 生命周期管理；API 12+ 可用。官方实践：进编辑器时执行一次，不要每次手势重跑。
- **对移植的意义**："移除背景"（SubjectRemoval）可直接落地。"对象选择"（点击选前景物体）可用 `maxCount>1` + details 近似源项目 Vision 前景实例蒙版的效果——**逐实例掩码的具体形态需实测确认**（答文只描述了 fullSubject 输出）。
- **⚠️ 核验/实测**：多主体时掩码是逐主体数组还是整体一张；大图分辨率建议（答文无硬性上限，实测 >12MP 是否需降采样）。
- **注**：答文"不支持 Android 的 API 24"表述混乱，实义是"HarmonyOS API 12+ 可用"，与我们的 API 24 目标无冲突。

### Q9 文字工具 → 能力齐备 ✅

- **结论**：
  - 字体注册：`font.registerFont`（全局）或 `FontCollection.loadFontSync/loadFont`（@kit.ArkGraphics2D，支持 rawfile/沙箱路径）；注销 `unloadFontSync` API 20+。
  - 自绘富文本：`ParagraphBuilder` → `buildLineTypeset()` → `createLine` → `getGlyphRuns()`（逐 run）→ `getGlyphs()/getFont()/getAdvances()`（API 20+）→ `TextBlob.makeFromRunBuffer` → `canvas.drawTextBlob`。即**逐 run 测量/排版/自绘的完整链路存在**。
  - 系统字体：`font.getSystemFontList()` 枚举（约 50–100 款）、`getFontByName()` 查元数据（path/weight/italic/monoSpace）、`getUIFontConfig()` 回退策略。
- **对移植的意义**：TypeTool 的核心链路（字体列表选择 → 逐 run 样式 → 画布内绘制）在鸿蒙侧完整可对应，走 ArkGraphics 2D（注意：这属于 Canvas/RenderNode 体系，与 Q4 定的 GLES 自绘管线并存——文字层可以直接画进 GL 纹理（TextBlob → 像素 → 上传），与源项目 draftTextCache 位像化思路一致）。
- **⚠️ 核验**：`getAdvances`/`unloadFont` 的 API 20+ 要求（我们 24 满足）；TextBlob 绘制到离屏 buffer 的路径。

### Q10 浮动面板 → Stack 覆盖层 ✅

- **结论**：**强烈推荐应用内 Stack 覆盖层，不建议 SUB_WINDOW**。子窗口是独立窗口：主窗移动/缩放需手动同步坐标（延迟与误差）、焦点抢占、事件透传难做精细控制；Stack 组件天然对齐父容器、跟随同步、`hitTestBehavior` 可精细控制穿透（非模态要求"面板开着还能画"）。
- **对移植的意义**：源项目 FloatingPanel（NSPanel）→ Stack 覆盖组件（offset/position + zIndex + hitTestBehavior）。曲线/色阶/滤镜面板、Camera Raw 停靠面板全部走这条路。
- **与知识库互洽**：面板内容仍可配 CustomDialog/Dialog 能力，但载体是应用内组件。

### Q11 菜单栏 → 自绘 ✅

- **结论**：**鸿蒙没有系统级应用菜单栏注册 API**（window 能力只有状态栏/标题栏属性）。方案：窗口顶部自绘 Row 菜单条 + `bindMenu`/`Menu` 弹下拉；菜单项使能状态走状态管理。
- **对移植的意义**：源项目的巨型 `.commands` 菜单体系（几十个菜单项 + 快捷键标注）需要自建一套数据驱动的菜单栏组件。这其实对移植有利：菜单数据模型（名称/快捷键/使能/回调）可以与 Q12 的快捷键系统共用一张表（对应源项目 ShortcutDefinition.all 的设计）。

### Q12 快捷键与焦点 → 应用内方案 ⚠️

- **结论**：
  - **无系统级全局快捷键 API**；应用内部用根节点/页面根 `.onKeyEvent` 统一监听，组合键判断 `event.ctrlKey/shiftKey/altKey`（答文自己标注"字段名需按实际 API 版本确认"）。
  - 焦点切换：`focusControl.requestFocus('key')` + 组件 `focusable(true)`。
  - 修饰键按住状态：单独按下 Ctrl/Shift/Alt 也会触发 KeyDown/KeyUp（`KEYCODE_CTRL_LEFT` 等），自维护状态变量。
- **对移植的意义**：源项目 KeyboardShortcuts 系统（Chord 位编码 + UserDefaults + 冲突校验）可平移，事件源从 NSEvent 换成 onKeyEvent。**画布默认持有焦点**是编辑器体验的关键（等价源项目 canvasFocusRequest 机制）。
- **⚠️ 核验**：KeyEvent 的 `ctrlKey/shiftKey/altKey` 字段在 API 24 d.ts 的准确名称；根节点 onKeyEvent 是否要求子树持有焦点（决定"画布无焦点时快捷键是否生效"——**这是高风险点**，若 onKeyEvent 依赖焦点链，需保证画布节点常驻焦点）。

### Q13 鼠标/笔细节 → 基本可行 ⚠️

- **结论**：
  - 自定义光标：系统光标样式有限 → **覆盖层组件跟随鼠标**（Circle + @State 坐标 + `HitTestMode.None` 不拦截事件）。
  - 滚轮：`onMouseEvent` 判 `mouseAction == MouseAction.WHEEL`，读滚动量（答文写 `wheelDeltaY`，标注"或类似字段"）。
  - 触控笔：TouchObject 读 `pressure`（0–1）、`tiltX/tiltY`。
- **对移植的意义**：画笔光标（BrushCursorOverlay）、滚轮缩放、压感笔刷（源项目有 MetalBrushCoverage 密度积分，压感可直接进 dab 参数）均有对应路径。
- **⚠️ 核验**：`MouseAction.WHEEL` 与滚动量字段在 API 24 d.ts 的准确名称（**高风险点**：滚轮缩放是桌面编辑器核心交互，若字段不存在需找替代——如 PanGesture 鼠标模式/`onMouse` 的 wheel 事件变体）；`tiltX/tiltY` 字段；另外 SDK 里可能存在组件级 `cursorStyle` 属性可设部分系统光标，一并核验后择优。
